## 1. 部署与启动

```bash
# 方式 A：源码直跑（Python 3.12+，运行时仅依赖 numpy）
pip install --no-index --find-links wheels -r requirements.txt   # 离线环境
python run_server.py 8765 --data-config company_data/config.json

# 方式 B：Docker
docker compose up -d
```

内网建议设置访问令牌（不设置时默认本机使用）：

```bash
export T2_AUTH_TOKEN=<随机长串>
# 客户端请求带 header:  Authorization: Bearer <token>
```

所有 API 调用写入 `runtime_data/audit.log`（JSON Lines，含时间、事件、客户端 IP）。

## 2. 数据模型总览：七张契约表

系统消费的逻辑表共七张。**只有 metric_panel（或 tracking_events）、change_registry、external_events 三张必填**，其余按数据准备程度逐步补齐——补得越多，归因解释力越强。

| # | 表 | 必填 | 粒度 | 服务的管线 |
|---|---|---|---|---|
| 1 | `metric_panel` | ✅* | 天 × region × channel × version | B 线基线归因 + 分层 RCA |
| 2 | `tracking_events` | ✅* | 一行 = 一次埋点事件 | 聚合生成 metric_panel（*两者至少给一张） |
| 3 | `change_registry` | ✅ | 一行 = 一次已登记变更 | B 线"已验证解释" |
| 4 | `external_events` | ✅ | 一行 = 一个外部事件窗口 | B 线时间关联 |
| 5 | `factor_snapshots` | 可选 | factor × 天 | 三层派生（Level/Velocity/Acceleration）关联发现 |
| 6 | `experiment_readouts` | 可选 | 一行 = 一个实验的 ATT 读数 | 变更的解释力来源 |
| 7 | `experiment_exposures` | 可选 | 一行 = 一个主体的实验分组 | A 线门禁与效应估计 |

**数据流关系：**

```text
tracking_events ──聚合──> metric_panel ──┬──> 持续对照基线归因（未知桶/阶跃报警）
                                         └──> rate-aware 分层 RCA（异常切面定位）
change_registry + experiment_readouts ──> 已验证解释（无读数的变更保持未解释）
external_events + factor_snapshots ─────> 候选关联（时间/滞后/范围对齐 + 留出窗复核）
experiment_exposures ───────────────────> A 线实验完整性门禁 + 贝叶斯决策
```

## 3. 埋点数据怎么给（tracking_events → metric_panel）

### 3.1 表结构

| 列 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `day` | int | ✅ | 相对日序号（0 起）。导出时把业务日期减去基准日即可 |
| `event_name` | str | ✅ | 事件名，如 `impression` / `click` / `submit` / `pay_success` |
| `subject_id` | str | ✅ | **散列后的主体 ID**（sha256+盐，盐留在公司侧）。明文手机号/身份证会被契约层直接拒绝 |
| `arm` | str | ✅ | `control` 或 `treatment`。control 必须是**持续对照基线**（长期持有、不受策略变更影响） |
| `region` / `channel` / `version` | str | ✅ | 分层维度。值域保持稳定，不要中途改口径 |
| `value` | number | 可选 | 金额类事件的取值（保费、GMV 等） |

### 3.2 聚合口径（系统自动执行，此处为对齐用）

只给埋点明细时，适配器自动聚合为 metric_panel，口径：

```text
对每个 (day, region, channel, version, arm) 单元格：
  分母 impressions = config.denominator_event（默认 impression）的事件条数
  分子 clicks      = config.numerator_event  （默认 click）     的事件条数
```

- 分子/分母事件名可在 `config.json` 里改（如分母=`quote_view`、分子=`pay_success`）；
- **去重粒度请在导出侧保证**（如按 subject_id+day 去重后再导出，或在导出 SQL 里 `COUNT(DISTINCT subject_id)`）；
- 中间转化事件（非分子/分母）不计入比率面板，不参与聚合；
- 聚合产物会再过一遍 metric_panel 契约校验（0 ≤ clicks ≤ impressions 等），口径错了会在启动时显式报错，不会带病运行。

## 4. 指标面板表逐字段说明（metric_panel）

| 列 | 类型 | 必填 | 校验规则 | 业务含义 |
|---|---|---|---|---|
| `day` | int | ✅ | 全部表的天轴必须对齐 | 日序号 |
| `region` / `channel` / `version` | str | ✅ | (day,region,channel,version) 全表唯一 | 分层三维，可按公司实际改语义但保持粒度稳定 |
| `control_clicks` / `control_impressions` | number | ✅ | 0 ≤ clicks ≤ impressions，impressions > 0 | 持续对照组的分子/分母 |
| `treatment_clicks` / `treatment_impressions` | number | ✅ | 同上 | 处理组（全量经营流量）的分子/分母 |
| `missing_rate` / `late_arrival_rate` | number | 可选 | 有限值 | 数据质量探针，会进入因子候选的 data_quality 层 |

**关键概念——持续对照基线**：control 列不是"上周同期"，而是一个长期持有、不随经营策略变化的对照组（如 1%~5% 长期 holdout）。这是 B 线一切结论的地基：gap = treatment − control 自动抵消季节性和大盘波动。没有持续对照的公司，先建 holdout 再用本系统。

## 5. 变更登记 / 外部事件 / 因子快照 / 实验读数

### change_registry.json（必填）

```json
[{"change_id": "chg_ranking_v3", "start_day": 15, "scope": "search_ranking",
  "experiment_id": "exp_ranking", "owner": "growth", "registered": true}]
```

- `experiment_id` 指向 `experiment_readouts` 里的 ATT 读数；**有读数才参与"已验证解释"**，没有就保持未解释（不会静默吸收）；
- 没登记的变更不用写——系统靠阶跃检测自己发现，这正是要验证的能力。

### external_events.json（必填）

```json
[{"event_id": "ext_regulation_0901", "kind": "regulation", "start_day": 45, "end_day": 49,
  "source_type": "authorized_external_event", "source_uri": "company://policy-feed/0901",
  "license_ref": "company-authorized", "claim_type": "TEMPORAL_ASSOCIATION"}]
```

- 每条必须带来源（`source_uri`）和授权标识（`license_ref`），这两个字段会进入 Claim Ledger，决定结论能升到什么证据等级；
- 外部事件永远只能得到 `TEMPORAL_ASSOCIATION` 等级，不会被写成因果。

### factor_snapshots.csv（可选但强烈建议）

`factor_id, day, value, scope_id, unit`——内部可观测指标（错误率、延迟、CPC、SLA）和外部序列（汇率、竞品强度、搜索热度）都放这里。系统会自动做 Level/Velocity/Acceleration 三层派生后进入候选搜索。**给的因子越全，未知桶越小。**

### experiment_readouts.json（可选）

```json
[{"experiment_id": "exp_ranking", "att_estimate": 58.2, "att_se": 6.1}]
```

历史实验的 ATT 点估计与标准误。提供后，对应变更的线上效果会被实验读数精确解释；不一致部分进入解释赤字报警。

## 6. 实验暴露表（experiment_exposures，A 线用）

| 列 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `experiment_id` | str | ✅ | 与 change_registry 联动 |
| `subject_id` | str | ✅ | 散列主体 ID（同样有明文拒绝护栏） |
| `variant` | str | ✅ | 分组，如 A / B / bundle_x |
| `day` | int | ✅ | 暴露日序号 |
| `converted` | bool | 可选 | 是否转化，用于门禁后的效应估计 |

A 线用这张表跑 8 项实验完整性门禁（SRM、平衡、分流稳定、污染、时间顺序、漏斗、cluster、并发实验）和贝叶斯决策层。**门禁不过的实验不会出决策建议。**

## 7. 常见数仓导出 SQL 模板

### Hive / Spark SQL（埋点 → 面板）

```sql
SELECT datediff(event_date, '2026-01-01')           AS day,
       region, channel, app_version                 AS version,
       arm,
       event_name,
       sha2(concat(user_id, '${salt}'), 256)        AS subject_id
FROM   dwd_tracking_event_di
WHERE  event_date BETWEEN '2026-07-01' AND '2026-09-30'
  AND  event_name IN ('impression', 'click')
  AND  arm IN ('control', 'treatment');
```

### MySQL（变更登记表）

```sql
SELECT change_id,
       datediff(effective_date, '2026-01-01') AS start_day,
       scope, experiment_id, owner, TRUE AS registered
FROM   growth_change_registry
WHERE  status = 'online';
```

导出为 UTF-8 CSV / JSON 数组即可；列名不同用 `config.json` 的 `field_mapping` 映射。

## 8. 启动验证与结果解读

```bash
curl -H "Authorization: Bearer $T2_AUTH_TOKEN" http://127.0.0.1:8765/api/health
# -> {"company_data": true, ...}

curl -H "Authorization: Bearer $T2_AUTH_TOKEN" \
  "http://127.0.0.1:8765/api/track2/scenario-run?scenario=company_line_b"
```

结果怎么读（与人工复盘对照）：

1. `unregistered_alerts`：系统检出的未登记变更起点 → 对照发布记录/运维日志，Top-k 命中即算法有效；
2. `association_discovery.candidates`：因子候选及关联强度 → 与分析师人工归因清单做 Top-k 对照；
3. `unknown_bucket`：解释不了的残差量 → **值大不是系统失败，是数据入口不足的信号**；
4. `validation_plans`：每个候选的下一窗口验证设计 → 交给实验平台执行，下周期回收看验证通过率。

证据落盘：`runtime_data/evidence/T2-company-lineB.json`（含来源 provenance）。

## 9. 数据质量检查清单（上线前自查）

- [ ] 对照组是持续 holdout，不是同期环比数据
- [ ] 所有表的天轴对齐（同一基准日、同一时区）
- [ ] subject_id 已加盐散列（明文会被契约层拒绝，这是好事）
- [ ] (day, region, channel, version) 在面板中无重复行
- [ ] 0 ≤ clicks ≤ impressions 处处成立
- [ ] 变更登记的 start_day 落在面板天数范围内
- [ ] 外部事件都带 source_uri 和 license_ref
- [ ] 面板至少 20 天（后 1/6 自动作为留出验证窗）；建议 60 天以上
- [ ] 分层维度值域稳定（版本号口径中途不变）

任何一条不满足，启动或运行时会收到精确到"哪张表哪行哪列"的 `ContractError`——这是设计使然：带病数据不进入归因。

## 10. 边界与合规

- 数据仅在 `/api/track2/scenario-run` 调用时读入内存，不外发；
- `license_ref` / `source_uri` 进入 Claim Ledger，未授权来源的结论无法升级为 CAUSAL；
- 契约层主动拒绝疑似明文手机号/身份证号（11/15/18 位纯数字），请在导出侧脱敏；
- 本系统输出为经营决策支持，不构成投资建议；证据不足时拒答是正常行为。
