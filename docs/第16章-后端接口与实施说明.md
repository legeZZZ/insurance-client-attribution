# 第16章后端接口与实施说明

2026-09-17，覆盖16.1–16.4。沿用阶段D已实现的统计验证、技能G0–G6、灰度/回滚和常驻扫描，补齐并行分析、人工因子入网格与统一认知反馈。控制台仍暂缓；不触碰真实流量，不自改统计代码。当前实现为确定性分析师进程，模型参数不更新，不声称复现背景论文或保证准确率提升。

## 16.1 人在回路：可追溯的认知反馈

保留 `operation=feedback` 的 submit/read/queue/register_supplement/calibration，新增ledger。B线候选可通过原submit接入；C线推荐新 `operation=cognitive` 的respond/read，自动绑定真实告警的因子、范围、指标和来源类别。不存在或已撤销的告警拒绝，不能伪造source_kind影响预算。

三个触点：

- candidate_review：confirmed/rejected/supplemented。confirmed仅排入AWAITING_STATISTICAL_VALIDATION；rejected保留记录。C线respond必须提供alert_id，factor_id须匹配。supplemented还需supplement因子对象和factor_db_path；登记新事件到下一窗口。
- factor_supplement：operator、note、factor_id、current_window、available_day必填，可提供name、factor_kind和snapshots。每条快照有day/value，可带scope_id；拒绝重复/非有限值/未来快照。登记来源为human_reported（即方案中的人工来源）。只报告事件但未提供足够快照时保持待数据状态，不凭空生成0/1序列。
- alert_feedback：useful/false_positive。source_kind从真实扫描输入取；标签可以修订，最新版本参与预算校准。每个方向至少4个标签后，低命中方向权重0.5，高命中方向1.5；这是次窗扫描调度权重，不是显著性阈值、因果置信度或准确率保证。

所有标签与修订写入共享HypothesisRegistry的持久audit/feedback_events；ledger是可读取的认知标签账本视图，entry_type=HUMAN_LABEL，包含event_id、revision、supersedes、is_current。不会把人工标签写成统计因果结论，claim_promotion_allowed始终为false。

## 16.2 技能层递归

SkillGovernance.propose现为真正的独立进程分析：一批1–32条新轨迹、最多4个并发分析师、每个30秒期限，绑定输入摘要/trace_id。固定规则只能从实际重放通过的白名单操作生成patch；失败需有已验证修正，否则只保留负例。环境故障走ISSUE。分析进程无发布、数据库或业务执行接口。

主进程按when/action合并；同适用条件动作冲突则AUDIT_ONLY，不能多数投票或覆盖冲突。源证据、独立验证、独立审查、人审凭证、灰度监测、扩大发布、回滚继续复用原G0–G6；尚未通过这些门的技能不能被扫描执行。统计核心与证据门禁止成为可演化操作。

新增skills/export_markdown返回filename=SKILL.md、markdown、spec_digest与execution_eligible，可保存为可审阅文档。SKILL.md包含完整版本化规则、来源和适用域；导出文件本身不赋予上线资格。skills/learn_from_feedback同一event/name/context幂等，旧标签被修订后不能再次训练，换名或换范围复用同一已学习事件拒绝。

## 16.3 主动扫描与证伪

scan/configure新增可选factor_db_path。每次尚未冻结的新窗口按observed_through做as-of读取，且FactorRegistry.search_window必须不晚于当前window_id。新人工因子按登记时current_window+1才可入网格。

当前桥接支持完整global数值快照；显式输入同ID因子优先。缺失global快照或日期不完整时记录skipped，不补零、不跨范围混合。registry_intake记录加入/跳过因子与快照摘要。已完成窗口重复tick仍ALREADY_PROCESSED，不把后来的人工反馈或新因子回填进旧检验族；需要下一窗口运行。

实际扫描继续使用猎手提出假设、证伪者负对照/安慰剂/反转/holdout、形态适用性判断。标签改变排序和有限预算内的扫描方向；总检验预算及原始检验方法不变。WATCHLIST只表示值得观察；晋级候选需要独立后窗确认，人工确认仅进入验证队列。

## 16.4 连成后端闭环

统一入口示例（先通过scan/alerts取得真实alert_id）：

```json
{
  "operation": "cognitive",
  "parameters": {
    "db_path": "outputs/live/state.db",
    "action": "respond",
    "parameters": {
      "request_id": "review-001",
      "kind": "alert_feedback",
      "payload": {
        "alert_id": "替换为真实告警ID",
        "label": "useful",
        "operator": "运营人员标识"
      },
      "skill_name": "watch_skill",
      "context": {"workflow": "c_line"}
    }
  }
}
```

运行：

```sh
scripts/run_backend.sh request.json --output outputs/response.json
.venv/bin/python tools/check_chapter16_acceptance.py
.venv/bin/python tools/run_backend_tests.py
```

respond会持久记录RUNNING/COMPLETED/FAILED、反馈事件和后续注册/技能提案；相同request_id相同输入可重试，改内容拒绝，活跃并发处理返回BUSY。失败保存已完成的反馈步骤，后续幂等重试；进程退出后的RUNNING可恢复。false_positive只生成负例审计，不能伪造有效方法修正。未传skill_name/context时只记录反馈，后续可通过skills/learn_from_feedback显式提案。

完整顺序为：scan/configure（skill_name/context及可选factor_db_path）→start/launch→tick产生告警→cognitive/respond记录标签并生成技能候选→skills/review→freeze_suite/validate→approve→publish灰度→monitor独立新套件→publish扩大→下一窗口scan/tick读取符合范围与版本资格的技能。暂停/回滚仍用skills/suspend_scope、rollback。真实人员凭证由受信后端接入；自动测试使用明确fixture，不冒充生产身份。
