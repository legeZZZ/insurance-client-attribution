赛道二方案说明

方案定位

让保险经营归因先证明“有资格下结论”

这套方案不是自动生成增长结论，而是把业务问题、指标口径、数据质量、结构分解、因果门禁、实验草稿和监测回流串成一条可审计的 AgentTeams 控制塔。目标是先把“能不能下结论”证明清楚，再决定“结论是什么”。

核心链路

从问题到可审计结论

01 / INTENT

问题标准化

把“DAU 上升、保费下降”变成可执行的问题、范围和单位。

02 / CONTRACT

指标契约

锁定指标版本、owner、窗口、漏斗定义和结果口径。

03 / DATA

只读校验

做 schema、缺失、泄漏和权限检查，先把风险挡住。

04 / DIAGNOSE

结构分解

把流量、渠道、产品和人群拆成候选贡献，不急着说因果。

05 / GATE

因果就绪

检查语义、数据、设计、统计和治理五层门禁。

06 / ACTION

实验草稿

只有通过门禁才生成实验草稿、护栏和停止规则。

07 / REVIEW

监测回流

监测结果、复盘假设，并把规则回流成版本化资产。

Agent 组织

7 个 Agent 分工

  • intent：接收并标准化业务问题。
  • metric_contract：确认指标口径和版本。
  • data_acquisition：只读获取、画像与质量检查。
  • diagnostic：漏斗、产品结构、渠道和分群分解。
  • causal_evidence：因果门禁、Claim Ledger、合规约束。
  • experiment_planner：实验草稿、护栏和停止规则。
  • monitor_review：监测、复盘和 Playbook 回流。

13 个版本化 Skill

能力被拆成口径与数据、经营分析、因果与实验、治理与交付四组，分别对应 MetricContractResolver、SchemaProfiler、DataQualityGate、ReadOnlyQueryPlanner、FunnelDecomposer、ProductMixDecomposer、SegmentProfiler、EventAligner、CausalReadinessCheck、ExperimentPlanner、ExperimentMonitor、ClaimPolicyGuard 和 WeeklyBriefComposer。

推荐的数据文件形态

首选：CSV / Parquet / JSONL，一行一条观测。这样可以直接进入数据画像、分解和因果门禁。

如果只有聚合表：也可以，但只能做描述性分析，不能给因果结论。

必须排除的字段

PII、自由文本、未来结果、事后字段、行动后字段、以及所有会泄漏结论的信息。对于呼叫前预测，像 UCI 的 duration 这种后验字段必须屏蔽。
